# Bug 分析（Bug）

> 诊断与修复 bug 的完整方法论：根治优先、根因/补丁判定、补丁协议、反模式与模式审计。
> 诊断或修复任何 bug 前必读；修复记录模板见 [bug-record.md](../templates/bug-record.md)。

## Use when

- 用户报告或测试发现任何 bug、异常、性能退化时
- 声称「已修复」前（与 [verify.md](./verify.md) 铁律叠加）
- 决定「修根因」还是「打补丁」时
- 同类问题第 2 次出现、或批量修复复盘时（模式审计 §9）

## 1. 铁律：根治优先

优先修根因，不修症状。修复成立的前提是能回答两问：根因是什么？为什么这个改动会让根因消失（而非症状暂时不见）？答不上来 = 还没找到根因，继续排查（判定见 §4）。

补丁只能在「根治成本超出当前风险预算」时使用，且必须走 §6 补丁协议。

## 2. 诊断循环

```
复现 → 最小化 → 定位 → 根因 → 修复 → 回归验证
  ↑        ↓
  └── 每步有证据才前进，无证据退回上一步 ──┘
```

| 步 | 动作 | 完成判据 |
|----|------|----------|
| 1 复现 | 按报告路径重演，采集原始现象（日志/截图/录屏） | 至少复现一次，或证明无法复现（写明尝试矩阵） |
| 2 最小化 | 缩小触发条件到最小输入/最小操作序列 | 删掉任一条件现象消失 |
| 3 定位 | 沿调用链/数据流定位出错点（先怀疑最近变更） | 出错点 + 出错时的状态有证据 |
| 4 根因 | 回答「为什么这里会错」——找引入点与触发条件 | 根因能解释现象的全部特征 |
| 5 修复 | 在根因处修复；同根因的同类点一并处理 | 修复不改动无关行为 |
| 6 回归验证 | 按 [regression.md](./regression.md) 分级回归 | 原路径不再复现 + 无新回归 |

证据纪律：每步结论要有证据（日志/截图/DB 查询/最小复现用例）；「应该是」「看起来」不允许出现在诊断记录里。取证手段见 [evidence.md](./evidence.md)。

## 3. 三层分类（症状 / 根因 / 引入点）

一次修复必须分别记录三层，防止修了症状丢了根因：

| 层 | 问题 | 记录内容 |
|----|------|----------|
| 症状 | 用户看到了什么 | 现象、影响面、频率 |
| 根因 | 为什么发生 | 错误的机制、触发条件 |
| 引入点 | 谁在何时引入 | commit/PR、当时的决策背景 |

只修症状 = 必复发；只记根因不找引入点 = 同类问题继续滋生。

## 4. 根治 vs 补丁判定三问

修复合入前，对改动逐一回答；任一回答指向「补丁」→ 先做 §5 补丁链检查，不直接合入：

| # | 三问 | 根因倾向回答 | 补丁倾向回答 |
|---|------|--------------|--------------|
| 1 | 改动位于问题发生链的**上游还是下游**？ | 上游（成因侧） | 下游（症状侧） |
| 2 | **移除这个改动后**，问题会以何种形式复发？ | 不复发（同因消失） | 立刻原样复发 |
| 3 | 是否引入了**新的隐藏状态、魔法常量或额外复杂度**？ | 否 | 是 |

三问全过、且实际移除验证过 = 根因；出现任一补丁信号 = 该改动是补丁，停下回到根因继续排查。

## 5. 补丁链识别信号

同一问题被反复打补丁时，commit 历史会留下痕迹；出现任一信号 → 停下回到根因：

| # | 信号 | 含义 |
|---|------|------|
| 1 | commit 说明出现「兜底」「防御」「临时缓解」「补 XX 的缺口」 | 在给上一个补丁再打补丁 |
| 2 | 同一模块短期内第 2 次以上修**同类问题**（非同一 bug 重开） | 前几次多半是补丁，根因未触及 |
| 3 | 一个修复需要「配套」修复才能闭环 | 补丁互相依赖，未触及根因 |

## 6. 补丁协议（无法根治时三件事齐全）

<!-- CANON:patch-three -->

三件事缺一 = 不合格补丁，评审直接打回：

| # | 事项 | 要求 | 去向 |
|---|------|------|------|
| 1 | 代码注释说明 | 当时情况 + 为什么临时 + 根因方向，标 FIXME/HACK | 补丁代码处 |
| 2 | 登记技术债 | 现象/临时方案/根因分析/修复建议/**复发场景预估**（什么输入、什么时序会再触发）/当时考虑 | [debt.md](./debt.md) 登记簿 |
| 3 | 回访条件 | 写清「何时/由谁/按什么条件」回来根治 | 债务条目 + backlog 卡片 |

反例警告：打了补丁却什么都没写的代码，半年后会被当成正常逻辑复制三份——到那时修复成本翻倍。

反射/私有 API 类补丁：注释必须写明依赖的框架版本与内部字段名，升级前手动测试。

## 7. 系统性分析方法

| 方法 | 用法 | 适用 |
|------|------|------|
| 5 Whys | 连续追问根因，直到机制级解释 | 单点 bug 的根因 |
| 影响域搜索 | 用「引入点」的同类模式全库搜索同类点 | 系统性缺陷 |
| 测试先复现 | 先写失败测试锁定行为，再修复（红→绿） | 可测试的纯逻辑 bug |
| 双向证据 | 代码检查 + 运行时观测两路印证同一结论 | 结论易错/易误判时 |
| 变更回溯 | git bisect/最近 diff 定位引入 commit | 回归类 bug |
| 历史档案 | 查同类 bug 的历史修复与教训 | 复发类 bug |

误判防护（真实教训泛化）：

- 观测手段本身会造假象：日志被噪音淹没、截图哈希不稳定、单方向测试把「已到边界」误判为「滚动失效」——结论前先排除观测误差
- 环境差异先于代码差异：先证明 bug 在干净环境可复现，再怀疑逻辑
- 「自动化都过了」不构成否定 bug 的理由——时间性现象以人工验证为准（[verify.md](./verify.md) §8）

## 8. 反模式清单

| 反模式 | 诱因 | 后果 | 正确做法 |
|--------|------|------|----------|
| 魔法常量无实测依据 | 一行兜底看起来有边界 | 超出即复发；常量无从复核 | 结构性方案（增量/游标）；常量来自实测并注明来源 |
| 故意延迟显示，掩盖缺失的过渡 | 「秒开」体验变顺滑 | 欺骗感知；真实问题未解决 | 实现真正的过渡；加载态只在真正加载时显示 |
| 防抖/重试掩盖持久化或同步策略错误 | 缩小问题窗口快速止血 | 根因仍在；窗口内仍丢数据 | 修正策略（状态变更即持久化、原子写） |
| catch 吞掉取消/中断异常 | 看起来「稳」 | 取消被吞 → 泄漏、竞态、僵尸状态 | 先重抛取消/中断，再兜底其余 |
| 删数据自愈（损坏与临时错误混为一谈） | 一条命令恢复「可用」 | 临时错误也当损坏，丢全部数据 | 区分损坏（删/重建）与临时错误（重试/降级） |
| 状态变量散落（多游标/多标志位各自为政） | 加变量比抽抽象快 | 越加越多；reset 竞态 | 抽成状态机/领域模型（单一真相源） |
| 一个 commit 打包多项修复 | 省 commit 数 | 审计与回滚困难 | 一事一 commit；fix 与 refactor 分离 |

## 9. 模式审计

启动时机：大版本发布后、积压修复达到 10 个、或**同类问题第 2 次出现**（同根因再犯 = 结构性信号，立即启动）。

做法：抽样 fix commit（按类型过滤），逐个看实际 diff（不只看说明）→ 按 §4 判定三问统计根因/补丁比例 → 同类问题出现 2 次 = 结构性问题 → 抽抽象或改约定。

| 产出 | 去向 |
|------|------|
| 审计报告 | docs/research/主题/ |
| 债务登记（含复发场景预估） | [debt.md](./debt.md) / backlog 卡片 |
| 可沉淀的通用预防规则 | [code-style.md](../standards/code-style.md)，编码阶段拦截 |

## 10. 修复后的闭环

- 修复必须回归（分级见 [regression.md](./regression.md) §2）
- 证据随 commit 归档（[evidence.md](./evidence.md) §6）
- 修复记录用 [bug-record.md](../templates/bug-record.md) 随 commit 附上
- 补丁类修复登记技术债并排入回访（§6）
- 同类模式全库排查结果记录在案（影响域搜索）
