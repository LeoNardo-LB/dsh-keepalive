# 技术债务（Debt）

> 已识别但暂不解决的技术债务的登记纪律：登记而非解决，让后续接触者理解当时决策、知道偿还方向与入手点。
> 条目格式见 [debt-entry.md](../templates/debt-entry.md)；登记簿本体是项目 docs/architecture-debt.md（init.sh 已实例化）。

## Use when

- 接触被登记模块前（先读债务再动手）
- 临时补丁落地后（[bug.md](./bug.md) §6 补丁三件事联动）
- 任务中顺带发现债务时（登记不跑题）

## 1. 定位

- **登记而非解决**：条目是决策记录，不是待办任务；是否偿还、何时偿还写进条目
- **债务不等于待办**：可执行任务登记 backlog 卡片；本登记簿只承载「当前不改、但必须被记住」的决策
- 登记每条债务回答四问（缺任一条目不完整）：

| # | 问题 | 缺失后果 |
|---|------|----------|
| 1 | 为什么存在（背景）？ | 无法判断是否仍成立 |
| 2 | 为何暂不解决？ | 决策依据丢失，被误当疏忽 |
| 3 | 什么条件触发偿还？ | 债务无限期滞留 |
| 4 | 从哪入手（偿还建议）？ | 想偿还也无从下手 |

违反后果：不登记 → 后续者把临时方案当正解，债务变永债。

## 2. 登记触发

| 触发 | 说明 |
|------|------|
| 补丁协议联动 | 无法根因修复的临时补丁必须登记（补丁三件事之一） |
| 顺带发现 | 任务中发现的债务（死代码/反模式/缺口）只登记，不现场解决 |
| 可接受债务 | 主动决定「当前不改」的项登记并写明理由与触发条件 |
| 定期盘点 | 复审或发版时扫描新增代码中的债务苗头 |

## 3. 分类

| 分类 | 定义 | 偿还优先级 |
|------|------|------------|
| 架构违规 | 依赖方向/分层破坏，尚未修复 | 最高 |
| 测试缺口 | 高风险模块无覆盖 | 最高 |
| 性能 | 当前量级可接受，未来可能放大 | 中 |
| 遗留反模式 | 阻塞式/硬编码/死代码 | 低 |

## 4. 维护纪律

| 纪律 | 动作 | 违反后果 |
|------|------|----------|
| 改动相关模块前先读 | 接触被登记模块前先查登记簿 | 重复踩坑、重复分析 |
| 新债务即登记 | 新发现即登记，禁止「先记在脑子里」 | 信息丢失 |
| 偿还时机 | 随相关重构顺带偿还；偿还后更新状态并留「为何当时不改」 | 债务遗忘、背景丢失 |
| 定期复审 | 随发版复审条目是否仍成立（外部条件可能使债务自动消失） | 条目与现实脱节 |

### 4.1 grep 检查规则

用自动化检查验证承重规则未被破坏，检查脚本进 CI 或定期运行：依赖方向禁令、硬编码禁令的检查命令模板见登记簿 §检查规则（实例化时按项目填充）；结果应为空。

违反后果：只靠人工审查 → 违规静默累积，债务条目失效。

### 4.2 偿还流程

```
接触被登记模块
  → 读登记簿中该模块条目
  → 评估：条件触发？随本次改动顺带偿还？
  → 偿还：按「偿还建议」执行 → 更新条目状态 + 留「为何当时不改」
           → 跑回归（regression.md §2 分级）
  → 不偿还：更新条目（现状变化）后继续原任务
```

偿还动作：偿还时同步更新相关文档（单一真相源：一处定义一处改）。
