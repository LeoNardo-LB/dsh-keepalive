# 完成验证（Verify）

> 声称任何任务完成前的唯一验证权威：铁律、五维证据框架、交叉验证矩阵、人工门禁与降级纪律。
> 本文回答「我算完成了吗」；「怎么拿证据」见 [evidence.md](./evidence.md)；「变更后重测什么」见 [regression.md](./regression.md)。

## Use when

- 声称任何任务/修复/功能「完成」前（必读）
- 不确定某个声明需要哪些验证证据、或证据是否构成交叉时
- UI 变更涉及时间性现象（闪烁/动画/计时）需要人工验证时

## 1. 铁律

```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

声称前五步（IDENTIFY → RUN → READ → VERIFY → ONLY THEN）：

| # | 步骤 | 动作 |
|---|------|------|
| 1 | IDENTIFY | 什么命令能证明这个声明？ |
| 2 | RUN | 执行完整命令（新鲜、当前消息内执行） |
| 3 | READ | 读取完整输出，检查退出码，统计失败数 |
| 4 | VERIFY | 输出是否确认声明？ |
| 5 | ONLY THEN | 才能做出声明 |

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 证据必须在当前任务中重新执行；引用上次运行/上次会话 = 虚假完成声明 | 陈旧证据不可复核 |
| 2 | 完成声明前已读本文（MUST 文档） | 遗漏验证维度 |
| 3 | subagent 报告 DONE 不信任，主 agent 独立复核后才采信（§6） | 虚报进入主线 |

## 2. 五维证据框架（命名维度）

| 维度 | 名称 | 手段 | 覆盖声明 | 通过标准 |
|------|------|------|----------|----------|
构建 | build | 编译检查 + 静态检查（命令真相源：[stack-profile §5](../stack/stack-profile.md)） | 代码可构建、无静态错误 | BUILD SUCCESSFUL / 0 errors |
测试 | test | 单元测试强制重跑（防增量跳过） | 逻辑正确性 | 0 failures |
运行时 | runtime | 模拟器/集成/UI 自动化实际运行 | 用户可见行为 | 全流程通过 + 断言全过 |
遥测 | telemetry | 日志断言 + DB 直查 + 网络直测（手段见 [evidence.md](./evidence.md)） | 健壮性与内部状态 | 增强测试全过 + 观测值符合预期 |
人工 | human | 用户按清单操作并反馈 | 时间性/主观现象 | 用户反馈记录 |

全系统统一使用以上五个**命名维度**；[regression.md](./regression.md) 的回归维度是同一组名称的回归视角，不再另设编号。

运行时维度禁止项（任一即完成声明无效）：

| 禁止 | 后果 |
|------|------|
| 仅编译不运行（如只编译插桩测试） | 编译通过 ≠ 运行通过 |
| 仅创建自动化脚本文件不实际运行 | 无实机证据 |
| 「上次运行是通过的」 | 非新鲜证据，违反铁律 |

## 3. 交叉验证矩阵（同结论 ≥2 独立维度）

### 3.1 结论类型 → 必选维度组合

| 结论类型 | 必选组合（≥2 个，建议 3 个） |
|----------|------------------------------|
| 逻辑/状态修复 | 构建代码检查 + 遥测 [+ 运行时] |
| UI 行为修复 | 运行时 + 遥测 [+ 构建] |
| 崩溃/异常修复 | 遥测（日志消失）+ 运行时（原路径重跑）[+ 构建] |
| 数据/存储修复 | 遥测（落库值正确）+ 构建 [+ 运行时] |
| 性能/时间性修复 | 运行时 + 人工 |
| 文案/i18n | 运行时（界面可见）+ 构建检查脚本 |

### 3.2 独立性判定（不同证据源才算交叉）

| 判定 | 示例 |
|------|------|
| ✅ 有效交叉 | 日志事件（遥测）+ 截图可见（运行时）：观测通道不同 |
| ✅ 有效交叉 | 单元测试断言（测试）+ DB 落库值（遥测）：验证层次不同 |
| ❌ 无效交叉 | 两张不同时刻截图（同属运行时，单维度） |
| ❌ 无效交叉 | 代码检查 + 同一次编译输出：可证「编译通过」，不可证「功能正确」 |

### 3.3 无法交叉时的处理

| 场景 | 处理 |
|------|------|
| 时间性现象自动化无法覆盖 | 走人工维度清单（§8），标注「自动化未覆盖，待用户确认」；不得声称完成 |
| 环境受限（无设备/模拟器） | 标注缺失维度 → 降级为部分验证（§7）→ 登记待补 |
| 维度冲突（日志说 A、UI 显示 B） | 以遥测为准排查；冲突本身是 bug 证据，记录归档 |

## 4. 每任务验证流程与完成清单

顺序：先写测试 → 实现 → 编译 → 提交。

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 测试先行（红 → 绿）：先写失败测试证明测试有效，再实现到通过 | 测试与实现脱节 |
| 2 | 每任务至少完成构建 + 相关测试两个维度 | 完成声明缺证据 |

阶段完成清单（声称前逐项核对）：

| # | 检查项 | 维度 |
|---|--------|------|
| C1 | 编译通过（当前消息内执行） | 构建 |
| C2 | 全量单元测试通过（强制重跑，0 failures） | 测试 |
| C3 | 新增代码有增强测试（边界/异常/并发） | 测试 |
| C4 | 涉及 UI 的变更：自动化用例实机运行通过（非仅编译） | 运行时 |
| C5 | 关键业务路径有可观测输出且符合预期 | 遥测 |
| C6 | git diff 审查无预期外改动 | 构建 |
| C7 | 时间性/主观现象：人工清单 + 用户反馈记录；无此类现象注明理由可跳过 | 人工 |

## 5. E2E 分档

| 档位 | 目标 | 通过标准 | 触发时机 |
|------|------|----------|----------|
| 冒烟档 | 快速验证核心链路无回归（≤15 分钟） | 核心 flow 全部通过 + 断言通过 + 无崩溃 | 每阶段收尾、发版前置；冒烟失败 → 转全面档定位 |
| 全面档 | 全量验证（含完整旅程与专项） | 全部 flow + 全量实机 + 全量单测 + 构建 全部通过 | 正式发版前、大版本/跨层重构收尾 |

回归策略：变更相关 flow 必跑 + 冒烟档全跑 + 全量兜底；flow 清单由项目按能力域维护（清单模板：[templates/ability-domains.md](../templates/ability-domains.md)）。

大型 E2E 验证拆双文档（期望 + 实操），模板：[e2e-plan.md](../templates/e2e-plan.md) / [e2e-runbook.md](../templates/e2e-runbook.md)。

## 6. Subagent 验证协议

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | subagent 报告 DONE → 默认视为未验证 | 虚报完成直接进入主线 |
| 2 | 主 agent 独立复核：git diff 确认改动 + 运行构建 + 运行测试 | 未复核结果无效 |
| 3 | 复核失败 → 标记该结果不可信，重新派发 | 不可信结论被采纳 |

并行委派细节（节点划分/证据落盘/抽查复核）：[evidence.md](./evidence.md) §7。

## 7. 降级纪律（禁止静默降级）

| 情形 | 处置 | 违反后果 |
|------|------|----------|
| 环境受限（无设备/依赖不可达） | 标注缺失维度 → 降级为部分验证 → 登记待补 | 缺失维度被默认已覆盖 |
| 维度冲突 | 以遥测为准排查；冲突是 bug 证据 | 按错误维度下结论 |
| 任何降级 | 完成声明中显式写明降级维度与待补项 | 静默降级 = 虚假完成声明 |

铁律：无法验证不是「没做」，而是「做了且明确标注未覆盖」。

## 8. 人工维度（时间性现象门禁）

截图是静态快照、断言是布尔判定——以下现象自动化与截图无法可靠捕捉，必须由用户人工验证：

| 现象 | 典型表现 | 为什么自动化捕捉不到 |
|------|----------|----------------------|
| 闪烁 Flicker | 内容短暂消失/重现 | 截图只取一帧 |
| 动画过渡 Transition | 过渡跳变/生硬 | 断言只看终态，不感知过程 |
| 计时重置 Timer Reset | 计时被重置回零 | 静态断言看不出时序错误 |
| 布局跳动 Layout Jump | 加载后高度突变 | 截图看不出「从哪跳到哪」 |
| 滚动抖动 Scroll Jitter | 视口被拉回 | 截图无法表达运动轨迹 |
| 蒙版揭盖 Mask Reveal | 揭盖过程闪烁/提前露底 | 需连续观察全过程 |

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 变更涉及上表现象 → 提供人工验证清单并请用户验证后才可声称完成 | 时间性缺陷上线 |
| 2 | 自动化全部通过 ≠ 时间性现象正确，不构成证据 | 以自动化代替人工 |
| 3 | 用户反馈「看着不对」即进入修复循环，不因自动化通过而搁置 | 缺陷被掩盖 |
| 4 | 修复循环每次迭代重新构建安装，禁止口头确认 | 复验的不是修复后产物 |

清单模板与发版前走查路径：[manual-ui-checklist.md](../templates/manual-ui-checklist.md)。

## 9. 输出规范

验证结果必须附实际命令输出（含执行时间与结果），而非概括：

```
✅ 构建命令 → BUILD SUCCESSFUL in Ns（执行于 <时间>）
✅ 测试命令 → N/N tests passed, 0 failures（执行于 <时间>）
❌ 插桩编译 → FAILED: unresolved reference <符号>
```

禁止的声明格式：应该通过了 / 看起来没问题 / 上次运行是通过的 / subagent 说测试全部通过。

## 10. 红线汇总

| # | 红线 | 违反后果 |
|---|------|----------|
| 1 | 完成声明基于当前任务内重新执行的新鲜证据 | 陈旧证据 = 虚假声明 |
| 2 | 测试通过以实际运行结果为准（仅编译不算） | 编译通过 ≠ 运行通过 |
| 3 | 时间性现象有用户人工反馈后才可声称完成 | 闪烁/跳动上线 |
| 4 | subagent 声明经主 agent 独立复核后才采信 | 虚报进入主线 |
| 5 | 任何降级显式写明，不静默降级 | 缺失维度被默认已覆盖 |
