# 开发循环（Dev）

> 从任务到提交的完整开发循环、编辑协议、提交规范与并行纪律；任何代码编辑任务开始前必读。
> 编辑协议与提交规范是承重约束——违反会丢代码、毁回归。

## Use when

- 任何代码编辑任务开始前（先读，再动手）
- 任务切分、并行编辑、提交消息格式不确定时

## 1. 开发循环六步

| # | 步骤 | 做什么 | 完成判据（才可进入下一步） |
|---|------|--------|---------------------------|
| 1 | 任务 | 明确目标、范围与验收标准；歧义先提问澄清 | 能一句话复述「改什么、不动什么」 |
| 2 | 读 | 读 AGENTS.md 相关章节与索引文档；编辑目标文件前先读其当前内容 | 能找到待改符号的位置、调用方与既有约定 |
| 3 | 设计 | 确定修改点与影响面（代码/测试/文档）；跨层改动先读 [architecture.md](../standards/architecture.md) | 影响面清单完整，含需同步的测试与文档 |
| 4 | 编辑 | 按 §2 编辑协议做最小修改（见 §4 精准修改） | 仅目标文件被改动，无无关变更 |
| 5 | 验证 | 按 [verify.md](./verify.md) 执行相应维度（至少构建 + 相关测试） | 当前消息内有新鲜验证输出 |
| 6 | 提交 | 原子提交，消息符合 §3 模板 | git status 干净或仅剩有意未提交项 |

```
任务 → 读 → 设计 → 编辑 → 验证 → 提交（循环）
```

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 每步完成判据未满足前不得进入下一步 | 跳步 = 返工或虚假完成声明 |
| 2 | 验证证据必须在本轮任务中重新执行 | 陈旧证据违反 [verify.md](./verify.md) 铁律 |
| 3 | 禁止跳过读/设计直接改（步骤 2/3 合并跳过） | 影响面未知，改错层、遗漏调用方 |
| 4 | 禁止用「应该没问题」代替执行验证 | 未经验证的完成声明 |

任务澄清：步骤 1 对「改什么、不动什么」有歧义时，先向需求方确认再进入步骤 2；凭假设开工的返工成本高于一次提问。

## 2. 编辑协议

适用于大文件（单文件超过 1000 行）与承重文件（AGENTS.md 指定的关键文件）。

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 禁止跨 agent 并行编辑同一关键文件 | 并发写互相覆盖，代码丢失或回归 |
| 2 | 每次编辑前先读目标文件当前内容 | 基于陈旧内容编辑，覆盖已提交修改 |
| 3 | 每次编辑后运行编译检查 | 错误累积，无法定位失败源 |
| 4 | 编译通过后立即提交 | 未提交状态积累，回滚连带丢失已通过的修改 |
| 5 | 编译失败：回滚该文件，重新读，再重试 | 带病继续编辑，掩盖真实错误 |
| 6 | 一次提交 = 一个逻辑变更 | 多变更混提，无法单独回滚 |

普通小文件可放宽「每次编译后提交」为「每个逻辑变更提交」；但「先读后编辑」与「禁止并行编辑」不放松。

## 3. 提交规范

消息模板：

```
<type>(<scope>): <祈使句摘要，不超过 50 字符>

- 需求/问题编号：<编号或 N/A>
- 变更内容：<改了什么>
- 验证：<构建/测试结果摘要>
```

type 取值：feat / fix / refactor / test / docs / chore。

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 一个 commit 只含一个逻辑变更（原子提交） | 无法按变更回滚、无法定位回归来源 |
| 2 | commit 消息关联需求/问题编号（无编号写 N/A） | 验收闭环断裂，无法追溯 |
| 3 | commit body 记录验证结果摘要 | 后续无法确认该提交是否经过验证 |
| 4 | 提交前 git diff 自查无预期外文件 | 测试产物、密钥等误入库 |

## 4. 精准修改原则

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 外科手术级修改：只改解决任务所需的最小代码集 | diff 膨胀，回归面不可控 |
| 2 | 不顺手修无关代码；发现无关 bug → 登记待办（[requirements.md](./requirements.md) §2），不现场修 | 任务范围膨胀、验证失效 |
| 3 | 格式/命名与既有风格一致，不顺手重排无关代码 | 格式噪音淹没真实变更 |
| 4 | 每处修改可对应到任务描述 | 无法验收，完成声明无依据 |

## 5. 并行工作纪律

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 按文件集合切分任务：并行 agent 持有的文件互不重叠 | 同文件写冲突，破坏 §2 协议 |
| 2 | 关键文件/构建配置由单一 agent 串行持有 | 覆盖丢失 |
| 3 | 并行前先定接口契约（签名、数据格式、状态机） | 集成时大量返工 |
| 4 | 一个 agent 一次只领一个完整可验证的任务 | 半成品互相依赖，无法独立验证 |
| 5 | 每个 agent 独立完成验证与提交后再合并 | 未验证代码进入主线 |
