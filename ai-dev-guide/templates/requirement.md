# 需求登记模板（Requirement Template）

> 需求条目的统一登记与验收格式：一个需求从登记到验收的字段全集，每份需求按此填写。
> 与 [../workflows/requirements.md](../workflows/requirements.md)（生命周期与验收闭环）配套：本模板定义「写什么」，流程文档定义「何时做」。

## Use when

- 登记新需求（用户提出 / backlog 提炼 / 审查发现缺口）时
- 需求进入开发前需要澄清、拆解、排期时

## 模板本体

新建需求条目时复制以下代码块，逐字段填写；无内容的字段填「无」，不要留空行：

````markdown
## <需求标题>

| 字段 | 值 |
|------|----|
| 状态 | <状态词取自 [../workflows/requirements.md](../workflows/requirements.md) §4 状态流转（唯一归宿，不自创）> |
| 优先级 | <P0 / P1 / P2 / P3，判据见 [../workflows/requirements.md](../workflows/requirements.md) §3（唯一归宿）> |
| 登记日期 | <YYYY-MM-DD> |
| 来源 | <用户 / backlog / bug / 代码审查> |

### 背景

<现状痛点与触发事件：为什么现在做，1-3 句，附数据或现象依据>

### 目标

- <做完后达成的可观测结果，逐条列出>

### 用户故事

- 作为 <角色>，我希望 <动作>，以便 <价值>

### 验收标准

- [ ] <可验证条件 1>
- [ ] <可验证条件 2：时间性现象加注 [人工验证]>

### 非目标

- <本次明确不做的事>

### 依赖

- <前置需求 / 第三方 / 数据 / 人力>

### 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| <风险描述> | <影响范围> | <缓解措施> |

### 工时估算

| 阶段 | 估算 |
|------|------|
| 澄清 | <人时> |
| 实现 | <人时> |
| 验证 | <人时> |

### 涉及模块

- <模块名 / 文件路径 / 文档链接>
````

## 字段填写说明

| 字段 | 填写要求 | 反例（违反后果） |
|------|----------|------------------|
| 状态 | 单选词表中的一个状态；词表与流转规则唯一归宿在 [../workflows/requirements.md](../workflows/requirements.md) §4，禁止在本卡自创状态词 | 留空（无法追溯进展，需求失联） |
| 优先级 | P0-P3 四级；每级判据唯一归宿在 [../workflows/requirements.md](../workflows/requirements.md) §3，禁止自创分级或漏级 | 自创分级（跨文档冲突，排期失真） |
| 背景 | 写现状与触发事件，1-3 句；不写解决方案 | 「增加导出功能」单句背景（无法判断为何做、何时算对） |
| 目标 | 可观测结果，每条至少对应一条验收标准 | 「提升用户体验」（不可验证，无法验收） |
| 用户故事 | 角色 + 动作 + 价值三要素齐全 | 「做一个设置页」（缺角色与价值，验收无锚点） |
| 验收标准 | 按下节「验收标准规则」逐条书写 | 模糊表述（验收时争议、声称完成无依据） |
| 非目标 | 明确写不做的范围 | 省略（需求蔓延时无依据阻止） |
| 依赖 | 写阻塞本需求的前置条件；未知写「未知：<方面>」 | 省略（排期被前置任务卡死） |
| 风险 | 每条含影响与缓解；风险未知也要声明 | 空白（未评估风险即开工） |
| 工时 | 分阶段估算，单位人时；超预期是澄清信号而非承诺 | 单个总数字（无法定位超时环节） |
| 涉及模块 | 具体到模块 / 文件路径；不确定写「待定，见 <链接>」 | 「全项目」（范围失控，回归范围不明） |

## 验收标准规则

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 每条必须**可验收**：写明判定方法（操作步骤 + 期望结果 / 数据断言 / 截图证据） | 不可验收 → 验收阶段争议，无法闭环 |
| 2 | 涉及**时间性现象**（闪烁 / 动画 / 计时 / 布局跳动 / 滚动抖动）的条目必须标注 **[人工验证]** 并附验证步骤——自动化无法覆盖，按 [../workflows/verify.md](../workflows/verify.md) 提供人工清单 | 未标注 → 自动化测试通过即声称完成，时间性缺陷漏检 |
| 3 | 可自动化的条目写自动化断言（测试文件 + 断言内容）；不可自动化的写操作步骤 | 全人工 → 回归成本高；全自动化 → 时间性现象漏检 |
| 4 | 每条验收标准与「目标」一一对应或可覆盖；目标无对应标准 = 该目标不可验收 | 目标与验收脱节 → 做完发现目标未达成 |
| 5 | 每条标准可判定通过/不通过；禁止「体验流畅」「正常」类措辞 | 判定模糊 → 验收无法收敛 |
