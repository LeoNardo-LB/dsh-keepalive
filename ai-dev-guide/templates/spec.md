# 设计文档模板（Spec Template）

> 在动手写代码前，把「要做什么、为什么这样做」写成可评审、可验证的设计文档；spec 批准后才进入 [实施计划模板](./plan.md) 拆实施步骤。

## Use when

- 需求达到写设计文档规模时（见 [../workflows/requirements.md](../workflows/requirements.md) §7 澄清与拆解）——先读本模板再填写
- 实现前、设计评审前（spec 是评审与验证的锚点）
- 设计发生变更、需要同步更新文档时

## 模板本体

新建 `docs/specs/YYYY-MM-DD-<kebab>.md`（active 目录；命名受 check.sh 门禁 10 约束）时复制以下各节，逐节填写；占位符一律用尖括号 <...>：

### 头部

```markdown
# <功能/改进名> 设计（#<backlog 编号>）

日期：<YYYY-MM-DD>
状态：<草稿 / 已批准 / 已实施 / 已归档>
位置约定：active 位于 docs/specs/；实现并验收后移入 docs/archive/specs/ 并更新本行与 backlog 卡片引用路径
```

### 背景与目标

> 写什么：列出待解决的问题，每项挂 backlog 编号（#N）；目标 = 问题解决后可见的结果。

- **#N** <问题一句话>
- **新增项** <来源：用户反馈 / 顺带发现；无编号则标注来源>

### 已探测事实

> 写什么：只写实测实证过的事实（读代码 / 实机 / 日志 / 抓包），每条标注「探测日期 + 手段」；写到能支撑后续决策即可，不展开分析。
> 🔴 事实与推论分离：只写事实，禁止推测冒充事实——这是防 agent 幻觉的关键设计；推论必须单独标注「待验证」，不得与事实混排。

1. **<事实标题>**：<实测结论>（探测日期 <YYYY-MM-DD>，手段：<读代码 / 实机 / 日志 / 抓包>）
   - 推论：<基于事实的推断，标注「待验证」>
2. **<事实标题>**：<实测结论>（探测日期 <YYYY-MM-DD>，手段：<...>）

### 现状代码链路

> 写什么：现有实现怎么走，精确到文件/类/函数，标注关键位置（✅ 正确 / ❌ 问题点），让读者不打开代码也能理解现状与改动位置。

- <入口 → 链路步骤 → 渲染/落点>（`<文件路径>:<行或函数>`）
- 已知问题点：<具体问题>（`<文件>:<行>`）

### 分节设计

> 写什么：按主题分节（每节一个主题），每个决策点写三行——方案 / 取舍 / 为什么；方案具体到签名或行为，「为什么」给理由而非复述方案。

#### 节 1 — <主题名>

##### <决策点>

- **方案**：<具体做法，落到函数/字段/行为>
- **取舍**：<放弃的备选方案 + 代价>
- **为什么**：<理由>

#### 节 2 — <主题名>

##### <决策点>

- **方案**：<...>
- **取舍**：<...>
- **为什么**：<...>

### 风险与回滚

> 写什么：本设计可能出错的地方 + 出错了怎么退回；每条风险给一个可执行的回滚动作，不留「到时候再说」。

| 风险 | 影响 | 回滚方式 |
|------|------|----------|
| <风险> | <影响面> | <回滚动作：revert 提交 / 关闭开关 / 保留旧路径> |

### 验证要点

> 写什么：本设计特有的验证点；通用验证走 [../workflows/verify.md](../workflows/verify.md) 框架，此处只列他人无法替你想到的点；每条可检查、可判通过/不通过。

1. <本设计特有的验证点 1>
2. <本设计特有的验证点 2>

### 变更记录

> 写什么：设计在实现/评审中的变化，按时间倒序追加；每条 = 日期 + 改了什么 + 为什么。

- <YYYY-MM-DD>：<变更内容 + 原因>

## 填写规则

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 背景与目标逐条挂 backlog 编号；无编号项标注来源 | 需求无追溯 → 验收时说不清「解决什么问题」 |
| 2 | 已探测事实只写实测内容并附探测日期与手段；推论单独标注「待验证」 | 推测冒充事实 → 决策建立在幻觉上 |
| 3 | 现状链路精确到文件:行，标注 ✅ / ❌ | 读者需自己翻代码 → 评审成本高、问题点漏看 |
| 4 | 每个决策点三行齐全（方案 / 取舍 / 为什么） | 缺取舍 → 备选方案与代价丢失，评审无法判断 |
| 5 | 每条风险附可执行的回滚动作 | 「到时候再说」→ 出错时无退路 |
| 6 | 验证要点只列本设计特有项；通用验证引用 verification 框架 | 与通用验证重复 → 篇幅膨胀、注意力稀释 |
| 7 | 变更记录按时间倒序追加 | 设计演进无痕 → 实现与设计脱节无法审计 |
