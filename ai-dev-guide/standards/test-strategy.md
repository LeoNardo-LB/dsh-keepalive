# 测试策略（Test Strategy）

> 测试金字塔分层、各层覆盖要求、Mock 纪律与测试纪律；决定「写什么测试、写到什么程度」。
> 具体框架与命令的真相源是 [stack-profile.md](../stack/stack-profile.md) §4（测试栈）与 §5（命令符号）；完成判定见 [verify.md](../workflows/verify.md)。

## Use when

- 编写测试、决定测试层级与范围时
- 新增代码不确定要配什么测试时

## 1. 测试金字塔

| 层 | 速度 | 数量 | 目的 |
|----|------|------|------|
| 单元测试 | 毫秒级 | 多 | 验证单个逻辑单元（状态、契约、计算） |
| 集成/插桩 | 秒级 | 中 | 验证跨组件协作与真实依赖注入 |
| UI 自动化 | 分钟级 | 少 | 验证用户可见关键路径，可自动断言 |
| E2E | 最慢 | 最少 | 验证端到端核心旅程（含后端） |

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 数量随层上移递减（底层多、上层少） | 反馈慢、定位难 |
| 2 | 下层失败优先在下层修复，不用上层测试掩盖 | 缺陷被上层噪声掩盖 |
| 3 | 金字塔失衡（上层爆炸、下层空）时先补下层 | 验证成本失控 |

## 2. 覆盖要求表

| 代码类型 | 最低覆盖 |
|----------|----------|
| 模型/sealed class | 全分支 + 边界值 |
| Mapper/工具函数 | 正常路径 + 空/异常输入 |
| Repository 实现 | Mock 外部依赖 + 状态变化 |
| ViewModel | State flow + 事件处理 |
| UseCase | 委托验证 + 异常传播 |

每个任务的增强测试检查单（全选才可声称完成）：

| 检查项 | 示例 |
|--------|------|
| 正常路径 | 输入有效，输出符合预期 |
| 边界值 | 空集合、最大值、零值、负数 |
| 异常路径 | IO 错误、超时、非瞬态错误 |
| 并发场景 | 多协程、状态竞争、竞态 |
| 数据不可解析 | 非法输入、缺失字段 |

## 3. Mock 策略与风险

| 风险 | 表现 | 对策 |
|------|------|------|
| 宽松 mock 静默返回默认值 | 未 stub 的调用返回空值/零/假，断言假绿 | 关闭宽松默认；每个用到的调用显式 stub |
| 显式 stub 但不断言 | 调用从未发生也不知道 | stub 后追加调用验证 |
| mock 过度（mock 业务逻辑） | 测试测的是 mock 而非真实行为 | 只 mock 外部边界（网络/DB/系统时间） |
| 共享可变 mock 状态 | 用例间相互污染 | 每用例重建 mock 实例 |

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 被 mock 的调用必须有显式返回值并断言 | 默认值假绿掩盖 bug |
| 2 | mock 默认值不等于真实行为，不写入断言依据 | 断言失去意义 |
| 3 | 断言期望值必须来自独立真相源（已知字面量/规格/算例），禁止按实现同样方式重算 | 同义反复测试，永不可能失败 |

## 4. 测试纪律

| # | 规则 | 违反后果 |
|---|------|----------|
| 1 | 失败测试必须分析根因后修复 | 失败被搁置，回归无声 |
| 2 | 禁止删除/注释失败测试让它通过 | 覆盖率假象，缺陷逃逸 |
| 3 | flaky 处理：定位根因 → 修复 → 连续重跑确认；暂无法修 → 登记待办并标注 | flaky 蔓延，验证不可信 |
| 4 | 重跑使用强制重跑选项，防增量跳过 | 陈旧结果冒充新鲜证据 |
| 5 | 测试与被测代码同 commit | 中间状态不可验证 |
| 6 | 测试命名表达行为（given_when_then 或等价） | 失败时无法定位意图 |

## 5. TDD 与否（决策表）

| 场景 | 是否用 TDD |
|------|-----------|
| 新业务逻辑（状态机/契约/计算） | 用：先写失败测试（红）→ 最小实现（绿）→ 重构保持绿 |
| 修复 bug | 用：先写复现失败的测试，再修到绿 |
| 纯 UI 布局/样式微调 | 不用：走 UI 自动化或人工清单（[verify.md](../workflows/verify.md) §8） |
| 一次性调研/脚本 | 不用 |

TDD 的产出物 = 回归测试 + 明确行为契约；不用 TDD 的改动仍需按 §2 配测试。

## 6. 哪些改动必须配测试

| 改动类型 | 必配测试 |
|----------|----------|
| 新增业务逻辑（状态/契约/计算） | 单元测试（含增强清单） |
| 修复 bug | 回归测试（先复现后修复） |
| 数据层改动 | 单元测试（Mock 外部依赖 + 状态） |
| ViewModel/状态流改动 | 单元测试（State flow + 事件） |
| UI 交互改动 | UI 自动化或人工清单（时间性现象必须人工） |
| 纯重构（行为不变） | 依赖既有测试（以既有测试全绿为证） |
| 文档/配置 | 不配测试 |
