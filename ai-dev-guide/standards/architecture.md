# 架构（Architecture）

> 分层与依赖方向、承重规则登记、深模块设计词汇、设计模式使用原则与「不过度设计」判据。
> 跨层改动、设计/修改任何模块接口前必读。

## Use when

- 新增/调整分层、修改模块边界或接口签名前
- 引入新的设计模式、新的抽象层、新依赖前
- 理解既有架构决策（ADR）时

## 1. 分层与依赖方向

```
<UI 层>        →  <领域层>   ←  <数据层>
只做展示与交互     纯业务逻辑     实现接口与外部交互
```

| 规则 | 说明 | 违反后果 |
|------|------|----------|
| 依赖方向单向 | 外层依赖内层，内层不依赖外层 | 领域被平台污染、无法独立测试 |
| 内层纯 | 领域层零平台依赖（无框架/无 UI/无 IO 类型） | 逻辑与平台绑定、迁移困难 |
| 接口向内定义 | 领域层定义接口，数据层提供实现（依赖倒置） | 换实现要动领域 |
| 越层直调禁止 | UI 不得绕过领域直接调用数据层实现 | 分层形同虚设 |

验证手段：依赖方向检查应脚本化（grep 禁止 import 模式，脚本模板见 [debt.md](../workflows/debt.md) §4.1）。

## 2. 承重规则（Load-bearing Rules）

定义：违反会引入回归的架构规则——不是风格偏好，是「动了会坏」的约束。

登记格式（每发现一条立即登记，最关键的 3-5 条内联进 AGENTS.md 架构概览段）：

```
### <规则名> 是 <某个关注点> 的单一真相源
- 规则：<一句话描述正确形态>
- 理由：<为什么必须如此（引用当初踩坑的记录）>
- 违反后果：<会坏什么>
- 验证方式：<grep 命令/测试/评审检查>
```

通用示例：

| 规则 | 正确形态 | 违反后果 |
|------|----------|----------|
| 状态单一真相源 | 所有状态写入经唯一服务 + 纯函数状态机，不按模块各存一份 | 状态互相覆盖、UI 闪烁、竞态 |
| 统一日志门面 | 新代码只走统一门面，不走平台裸日志 API | 日志不进诊断页、双份体系 |
| 边界处理统一工具 | 路径/解码/编码等跨平台边界只走统一工具函数 | 平台差异导致崩溃 |

## 3. 深模块设计词汇

| 术语 | 定义 |
|------|------|
| 模块 | 任何有接口和实现的东西：函数、类、包、跨层切片 |
| 接口 | 调用方正确使用必须知道的一切：签名 + 不变量 + 顺序约束 + 错误模式 |
| 深度 | 接口背后的行为量 ÷ 调用方要学的接口面：小接口 + 多实现 = 深；大接口 + 薄实现 = 浅（避免） |
| 缝（seam） | 接口所在的位置——「不改动此处就能改行为」的地点 |
| 适配器 | 在缝上满足接口的具体实现（描述角色而非内容） |

设计接口时三问：方法数能减吗？参数能简化吗？更多复杂度能藏进实现吗？

删除测试：想象删除该模块——复杂度消失 = 它是转发壳（多余）；复杂度在 N 个调用方重现 = 它在赚它的存在。
缝的判据：一个适配器 = 假设的缝；两个适配器 = 真实的缝。没有实际变化点就别引入抽象。

## 4. 设计模式使用原则

| 原则 | 说明 |
|------|------|
| 模式为问题服务 | 先有问题、后找模式；不为模式制造问题 |
| 优先语言内建 | 语言内建能力能解决的不用「模式」包装 |
| 状态用状态机 | 状态多、转移有约束 → 显式纯函数状态机（穷举转移、可测试） |
| 变体用策略 | 行为随类型变化 → 策略/多态；只变一次 → if 即可 |
| 单例谨慎 | 全局可变单例是隐藏依赖与测试污染源；需要时用 DI 作用域代替 |

| 模式 | 何时用 | 何时不用 |
|------|--------|----------|
| Repository | 隔离数据源、让领域面向接口 | 只有一个数据源且永不替换（先直连） |
| 状态机 FSM | 状态 ≥3 且转移有非法组合 | 布尔双态 |
| 策略/多态 | 同接口 ≥2 个真实实现 | 未来「可能」有第二个 |
| Observer/流 | 一对多、事件驱动 | 一次性回调 |
| 工厂 | 创建逻辑复杂/有分支 | new 就够了 |
| 装饰器/管道 | 横切关注点可叠加 | 单一职责直接实现 |

## 5. 不过度设计判据

| # | 判据 | 说明 |
|---|------|------|
| 1 | YAGNI | 不为「将来可能需要」写抽象；需要时再抽象（有测试保护，重构成本可控） |
| 2 | 两个适配器规则 | 只有出现第二个真实实现时才引入接口/抽象层 |
| 3 | 删除测试 | 抽象删掉后复杂度不回归 → 该删 |
| 4 | 复杂性预算 | 每个抽象必须比它消除的复杂度更便宜 |
| 5 | 直接性优先 | 先写直白代码，模式化是重构出来的不是设计出来的 |
| 6 | 接口面积 | 抽象后调用方要学的东西变多了 → 抽象失败 |

过度设计的信号：接口方法无人调用、抽象层纯转发、配置项永远只有一个值、测试比实现还复杂。

## 6. 架构决策记录（ADR）

以下决策必须写 ADR（模板：[adr.md](../templates/adr.md)；存放于项目 docs/specs/ 或 docs/adr/，验收后按 spec 生命周期归档），否则后续 agent 会在同一岔路口反复横跳：

- 跨层接口设计（为什么这样切分）
- 存储/同步方案选型（含被否方案）
- 引入新依赖/新框架
- 不可逆决策（协议、数据格式、迁移）

## 7. 架构文档维护

| 规则 | 违反后果 |
|------|----------|
| 改架构 → 同 commit 更新本文档 + AGENTS.md 架构概览段 | 文档与现实漂移 |
| 新增承重规则 → §2 登记 + 判断是否内联进 AGENTS.md | 规则散失 |
| 架构文档描述「为什么」与「规则」，不复制目录树（目录树真相源是文件系统本身） | 篇幅膨胀且必过期 |
