# 代码风格（Code Style）

> 代码的命名、格式、复杂度预算、注释与「AI 友好」实践规范。风格以外观为目标，AI 友好以**可被正确理解与修改**为目标。

## Use when

- 编写新代码、修改现有代码前
- 评审代码风格、清理遗留风格问题时
- 写任何注释（公开 API/模块/测试/README）前（§4 按位置覆盖矩阵）

## 1. 与语言官方规范对齐

| 优先级 | 来源 | 落地方式 |
|--------|------|----------|
| 1 | 语言官方 style guide | 直接遵循 |
| 2 | 社区主流惯例 | 遵循，记入本文件 |
| 3 | 本项目约定 | 必须登记在本文件，并写明理由 |

格式化交给工具，不靠人肉：formatter/linter 配置入仓库，CI 检查；本地不满足格式 = 构建失败。风格讨论的终点是「改配置并全员重跑」，不是口述规则。

## 2. 命名规范

| 对象 | 规范 | 反例 |
|------|------|------|
| 类/接口 | 名词短语，无动词 | MessageParser、ConnectionService（非 DoParse） |
| 函数/方法 | 动词开头，说清动作+对象 | parseEvent、computeUnread（非 handle、process 式空泛名） |
| 布尔变量 | is/has/can 前缀，正面表述 | isStreaming、hasUnread（非 notBusy、flag） |
| 回调/事件处理器 | on 加事件名 | onOptionClick（非 click1） |
| 常量 | 语义名，禁止魔法值内联 | MAX_CACHED_MESSAGES = 1000（非 1000 散落） |
| 临时变量 | 有含义；循环索引除外 | pendingIds（非 tmp、data2） |

- **可搜索性**：名字必须能成为搜索关键词（handleEvent 有 40 处调用时无法定位具体语义）
- **一个名字一种含义**：同一概念全仓库用同一词（session 不一会叫 chat 一会叫 conversation）

## 3. 函数与复杂度预算

| 指标 | 预算 | 超预算动作 |
|------|------|-----------|
| 函数行数 | ≤40 行 | 拆纯函数/子步骤 |
| 参数个数 | ≤4 个 | 收拢为参数对象/数据类 |
| 嵌套深度 | ≤3 层 | 提前返回（guard clause）、抽函数 |
| 圈复杂度 | ≤10 | 抽分支为独立函数或策略 |
| 文件行数 | ≤500 行 | 按职责拆文件（超 500 登记技术债） |

判据：一个函数「能做一件事且名字能说完这件事」为止；拆分的收益是可独立测试与可独立理解。

## 4. 注释覆盖矩阵（按位置定必写与禁写）

总原则：注释描述代码**不能表达**的非显性契约或理由；代码已能表达的（复述控制流、罗列做了什么）一律禁写。

| 位置 | 必写 | 禁写 |
|------|------|------|
| 公开 API（接口/公共类） | 契约、前置条件、错误模式、线程/协程语义、副作用与所有权 | 显而易见的签名复述 |
| 铁律处（承重逻辑） | 指向文档的指针注释：「铁律：必须用 X 工具处理路径，见文档链接——违反会引入回归」 | 只写「重要」不写后果 |
| 补丁处 | 当时情况 + 为什么临时 + 根因方向（[bug.md](../workflows/bug.md) §6 三件事之一） | 无登记的裸 FIXME |
| 内部注释 | 非局部结构定向、显性复杂局部结构的不变量/顺序/所有权/安全边界 | 控制流叙事（先做 A 再做 B）、代码复述 |
| 模块头 | 模块角色、依赖、职责、非显性架构选择（架构选择链接到归属文档） | 目录内容罗列 |
| 测试 | 为什么需要这个 fixture/断言/平台适配/间接观测 | 测试步骤走查、断言清单罗列 |
| 死代码 | 禁止注释掉的死代码：要么删，要么恢复；git 历史负责记忆 | 大段注释代码 |

标记语义：TODO = 计划内待办；FIXME = 已知缺陷；HACK = 有债临时方案（必带解释与登记）。

## 5. AI 友好编码实践

| # | 实践 | 为什么 |
|---|------|--------|
| 1 | 小纯函数：无副作用、输入输出显式 | 可测试、可推理、可安全复用 |
| 2 | 显式契约：类型/参数/返回说清，不靠隐式约定 | 调用方不读实现也能正确使用 |
| 3 | 单一职责：一个模块改动的理由只有一种 | 修改影响面可预测 |
| 4 | 不可变优先：状态变更收敛到少数明确入口 | 并发与重组下行为稳定 |
| 5 | 确定性优先：同输入同输出；避免依赖时间/顺序的隐式状态 | 测试可靠、调试可复现 |
| 6 | 不用巧妙技巧：晦涩写法必须注释，能用朴素写法的用朴素写法 | agent 与人都要能读懂 |
| 7 | 稳定接口：接口变化即破坏调用方，变化要显式、要回归 | 减少连锁修改 |
| 8 | 错误显式：不吞异常、不静默失败（[reliability.md](./reliability.md)） | bug 不被掩盖 |

删除测试（判据）：删除这段代码，它的职责会在调用方重新出现吗？会 → 值得存在；不会 → 可能是多余抽象。

## 6. 与架构规范的分工

- 本文档管**代码内部**（命名/结构/注释）；[architecture.md](./architecture.md) 管**模块之间**（分层/依赖/接口）
- 违反风格 → 评审打回；违反承重架构规则 → 直接回归风险
